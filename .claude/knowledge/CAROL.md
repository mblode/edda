# Carol — Blode.md

Carol is the ideal customer for Blode.md. Definition first. Keystones, deal-breakers, and inciting events below are the working files this synthesizes. Evidence is the public product record plus hypothesized triggers; no customer interviews yet.

This file is whose stack `NEEDS-STACK.md` belongs to, and whose language `POSITIONING.md` must speak.

## Definition

Carol is the person who already writes the product in git and is expected to write the docs in the same motion.

She ships a developer-facing surface — an API, SDK, CLI, library, or infra product — where the docs page _is_ how a user (and now a coding agent) learns the product. She authors Markdown or MDX in the repo, in the editor she already uses. The pull request is the only review she trusts. If a tool asks her to leave that editor for a CMS, she will not adopt it, even if the CMS is prettier.

She has watched docs lag a release at least once: the code merged, the Notion/GitBook page did not, and someone — a user, a teammate, or an agent — followed the old page. That mismatch is now a product bug on her scoreboard, not a "docs chore." She counts successful integrations and correct answers, not hours saved in a CMS.

She will not pay per-seat or per-page to host files she already wrote. She wants the public URL on the domain users already trust, usually `/docs` on the marketing site. She is fine with a small surface: no plugin marketplace, no second review flow. She will email a founder. She will not file an RFP that demands SOC 2, SSO, and a logo wall before she pushes a folder.

She is not a demographic. She is a circumstance: git-native writer, docs-as-code as the only acceptable review, agents already reading the output, seat-tax allergic, domain-proud, procurement-light.

The ring around her (Diana) shares the trade-offs and buys anyway: a small team whose one DX engineer is Carol; an open-source maintainer who wants MIT; a founder who is not yet drowning in agent tickets but refuses a second editor. Eddie is everyone else — do not write the homepage for Eddie.

## Keystones (why she buys from you)

- **K1** — The PR is the only review; a second editor splits the release.
- **K2** — Public docs origin must be the product domain (`/docs`).
- **K3** — Agents already answer from docs; Markdown must come from the same deploy as HTML.
- **K4** — Will not pay per-seat/per-page; MIT/self-host must remain possible.

## Deal-breakers (who is not Carol)

- **D1** — Will not use git/MDX; needs WYSIWYG/CMS.
- **D2** — Needs SOC 2, SSO/SLA, named CSM.
- **D3** — Needs a famous-vendor roster or a paid viability story before trying.
- **D4** — Must-have first-party themes, first-party analytics, or team-accounts product today.
- **D5** — GitLab/Bitbucket-only and will only accept a zero-config app on that host.

## Inciting events (why she buys today)

All hypothesized until onboarding interviews exist:

- **E1** — Last three PRs shipped; docs in Notion/GitBook did not.
- **E2** — Seat/page invoice she will not pay (use in ads/FAQ, not as the H1).

## How to use this

Marketing speaks K1 in the headline and E1/E3 in the commiseration line. Sales (when it exists) qualifies on git/MDX and disqualifies D1–D5. Product builds what thrills K1–K4 and does not build for D1.
